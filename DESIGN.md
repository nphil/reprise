# Reprise interface

## Direction

Reprise is an operating tool, not a promotional page. The user confirmed a **library-first, code-led** interface. There is no approved visual comp and no comp-fidelity claim.

The surface uses the Lucent v2 web adaptation, Rosé Pine dark/light roles and locally bundled Manrope. `media_preview_generator/web/static/css/reprise-tokens.css` is the token layer.

### One shell, two destinations

Every signed-in page extends `base.html` and gets the same sidebar. It has two destinations, **Library** and **Settings**. Its footer holds, in order: the Plex safety chip ("Review only" or "Plex publishing is on", from `GET /api/reprise/settings`), notifications, theme, Help, the Setup guide, the tour and Sign out. On phones the sidebar becomes a top bar with a menu button. Sign-in and the Welcome page are standalone (`_auth_page.html`); the setup wizard and the sign-out confirmation use the base without the sidebar (`rp_bare`).

Everything administrative lives under Settings, reached by one tab strip: Connections, Sharing, Automation, Advanced, Jobs, Logs, Inspector and Library health. Nodes belongs to Advanced and Webhook activity to Automation, and highlight those tabs. Plex publication and playback API clients ("Add an app") are on Sharing, not on the Library page, so the Library page has one job.

The inherited upstream pages keep their layouts. `reprise-shell.css`, loaded last, repaints them: it maps the upstream and Bootstrap variables (`--bs-*`, `--plex-orange*`, `--surface*`, `--t-*`) onto the `--lu-*` tokens and restyles cards, buttons, forms, modals, dropdowns, tables, badges and alerts. A page must never load the upstream navbar, its sponsor or "help the upstream project" links, or a "Media Preview Generator" page title. `tests/test_shared_shell.py` enforces this for every page.

### The primary flow

Library → pick an episode → Analyze → review the proposed intro and credits ranges → approve → save. Selecting several episodes analyzes them as one action. Approval stays separate from analysis and from publication.

### The Setup guide

A new install is not left to find its own way. `/setup-guide` (sidebar footer, and Settings, Advanced, Account) is a checklist of seven steps in two groups: **Required** (Connect Plex, Choose libraries and check your media folders, Refresh the library) and **Optional** (a graphics card, online intro lookup, Sonarr and Radarr, Send results to Plex). It is a page, not a dialog, and not a third destination: the sidebar keeps two, and the guide is a footer item for the same reason the tour is.

`GET /api/reprise/setup-guide` (owner only) computes every state from real configuration: saved settings, a few `stat` calls on the folders the libraries use, one indexed count in Reprise's own database, in-memory job, GPU and webhook state. It never asks Plex anything, walks no catalogue and never opens Plex's database. Each step comes back with a plain `reason`, optional `details` (one line per missing folder, saying what Plex calls it, where Reprise looks and which mount to add), copyable `values` and one button that opens the existing place that does it: the wizard, `/servers?edit=<id>&tab=paths`, the Library with `?refresh=1`, Automation, Sharing. The Sharing switch and step 7 read the same Plex-database findings, so they name the same missing folder.

Creating the account on a new install lands here (`/` goes to the guide while the saved choice is `pending` and a required step is open). The first-run tour opens by itself on the Library only, the page it explains, so it never covers the guide or the dialog and form the guide's buttons open (Connections' Edit, Automation, Sharing). **Skip for now**, offered once Plex is connected, saves `dismissed`; the three required steps being done saves `completed` by itself. An install that already has an account and a connected server counts as set up (its account file has no saved choice, which reads as `completed`), so the guide never opens by itself there and nothing is reset.

The page is a left-aligned column (at most 56rem). Each group is one bordered panel, no shadow, holding hairline-separated rows, not cards. A row is a 32 px marker (a check in a filled circle when done, the number in an outline when not, muted while waiting, a turning ring while a job runs), the title, a status chip that says the state in words, the reason, then details, copy fields and an external help link. The button sits under the text below 40rem (a container query on the panel, because the sidebar takes 232 px from 900 px up) and at the row's right edge above it; only the first not-done required step has a primary button. A re-check rebuilds only the rows that changed, so keyboard focus survives; the page re-checks when it becomes visible again and every 3 seconds only while a refresh runs.

## Library behavior

- The episode list is the left pane (sticky and bounded on wide screens, first in document order on narrow ones). Each row has a checkbox, the episode, and one plain status chip: Not analyzed, Waiting to analyze, Analyzing N%, N to review, Reviewed, Nothing to skip, Nothing found, Analysis failed, File changed, Cancelled, or Not supported. Counts reflect saved decisions only.
- Plex, media, part and audio identifiers are hidden. They appear only under the collapsed **File details** disclosure of the open episode.
- Every analysis outcome is a sentence with a next step, using the plain reasons the API returns (`reasons`, `outcome.message`, job `message`). The technical second line sits under **Details**. "Nothing found" says what was compared; a failure says why and offers Try again. A file that changed on disk offers Refresh library, not Analyze, because the backend refuses stale analysis.
- Activity, in the library pane, shows analysis, previews and library refresh jobs with progress and Pause, Resume and Cancel. A pause request is labelled pending until confirmed and offers Resume; terminal states remove controls. Only a refresh observed active triggers a one-time list reload when it finishes. It polls every 2.5 seconds while something runs and every 10 seconds otherwise.
- The page header says whether analysis decodes on a GPU or the CPU (`acceleration.label`) and offers "Use CPU only" or "Use GPU when available".
- Below the GPU line the header has one plain switch, "Look up intro times online (IntroDB, SkipDB)", on by default, saved through `PATCH /api/reprise/settings` (`online_lookups`) with one sentence saying what is sent (the show's id, season, episode and the file's length, nothing else) and that the times are only hints and suggestions you must approve. Online times only ADD places to search in other episodes; the strict sound and picture confirmation decides exactly as before, and with no online data a result and its speed are the same as before.
- Existing ranges start collapsed in native `details`, sorted by start time. Their summaries expose action, type, time bounds, decision and lock state. Fine timing, action, type and lock sit under "Fine-tune this section". New unsaved manual keep ranges open immediately.
- A section someone else suggested (`origin: "plex"` or `"online"`) is never presented as something Reprise found. It carries a badge naming who suggested it, "Plex suggestion", "IntroDB suggestion", "Plex + IntroDB suggestion" or "IntroDB + SkipDB suggestion" (after approval "<badge> · approved by you"), an outlined, unfilled bar on the timeline, and its own count in the list ("N to review" counts Reprise-confirmed skips only; "N Plex suggestions" counts the rest when every open one is Plex's alone, otherwise "N suggestions", and both can show). Choosing Approve on it opens an inline question, "<Names> found this, Reprise could not confirm it. Approve it only if it is right." (names joined with "and"; for Plex alone, "Plex found this, Reprise could not confirm it. Approve it only if it is right."), with "Approve it" and "Not now". Only after that answer does the save send `acknowledge_suggestion: true`, and only for that range: editing an already approved suggestion counts as the same deliberate act, while ranges re-sent untouched, rejected or undecided carry no flag. There is no approve-all, so a bulk action can never approve a suggestion.
- Range objects retain their own view while editing; typing and native select changes do not replace the focused field. Unsaved identity does not depend on array position.
- The save bar appears only when there are unsaved changes. The timeline is a visual overview; exact timings and decisions are in the range list.
- The selected episode is marked independently of focus, including after library reloads. `?search=` opens the Library filtered to a title (the Inspector links here).
- The list pane is a bounded column (sticky, at most the window's height): its head, filters and footer keep their size, the episode scroller takes what is left, Activity is capped in viewport units (a percentage cap does nothing in a pane with no fixed height) and scrolls on its own under its fixed head, and the selection bar is one row ("Analyze N episodes" and Clear). On a 1280×720 window with a running job, finished jobs and ticked rows the list still shows about three rows and nothing spills out of the pane. In windows under 660 px tall the pane stops being sticky, and below 1100 px (the sidebar takes 232 px of it) the list stacks above the review, with the "All episodes" link back. Ticking a row never moves the rows (the hint stays); "Select all" ticks every listed episode that can be analyzed now (not those whose file needs a refresh, not those being analyzed) and becomes "Deselect all"; ticked episodes the filters hide are counted ("2 not in this list"). Show and Season filters have no visible labels because their first options say "All shows" and "All seasons", and seasons read "Season 1".
- The open episode follows the list. A show, season or search that leaves it out closes it (back to the empty review, with "Closed <title>: it isn't in the filtered list."); with unsaved changes it stays open under a notice that says so, with "Clear filters" and "Close episode". The page decides with the service's own filter rule (show is a substring, season exact, search in title and show), so an episode on a page that has not been loaded yet is not closed by mistake. The empty review offers "Review next: <episode> (<status>)" for the first listed episode with something waiting for a decision.
- The status line (`#rpMessage`) is sticky and dismissible, so an error from the pane is visible wherever the page is scrolled. "Play this section" brings the player into view. A file the browser cannot play hides the empty player box until a preview works. A job's percent shows on an episode row only when the job holds that one episode. A changed file's chip, sentence and next step come from the service's `stale` object (`label`, `message`, `next`, `action`: `refresh` hides Analyze and offers Refresh library, `analyze` keeps Analyze and keeps the row selectable); a payload without it is shown as "File changed" with Refresh library.
- **Analyzing** means a thread of this process is carrying out that episode's analysis. The store keeps the ids of the runs it began and has not released (`begin_analysis` adds one before it writes anything; `run_job` releases it in a `finally`), and a run recorded as running that is not in that set is ended as Cancelled, "Analysis was interrupted before it finished", so the episode shows Try again instead of Analyzing for good. This happens at startup (`create_app` builds the one `RepriseStore` and ends what the previous process left running, which only a stop can have cut off) and whenever the service reads an episode's status. The container is stopped in the middle of an analysis on every redeploy, and a stored status that says running cannot know it: Community S1E04 showed Analyzing with no job behind it. It relies on one worker process (gunicorn `--workers 1`) and one store; with several, a run carried out by another process would look cut off.

## Intentional decisions

- Navigation is two items on purpose. A third top-level item needs a task that Library and Settings cannot hold.
- The Inspector's older "Check intro & credits" job is offered only when some server has that detector switched on. Otherwise it links to Analyze in Library, because that job checked nothing and looked as if it had.
- The master/detail review and lower administration sections scroll normally. They are not forced into a single desktop viewport. On narrow screens the library precedes review, with an "All episodes" link back; six range editors no longer all expand on arrival.
- Upstream documentation links (Nodes guide, Emby guide) still point at the preserved upstream guides. Reprise's own Help, release and update links point at `github.com/nphil/reprise`.
- The rendered Impeccable detector found one advisory earlier: repeated em dashes in explicitly synthetic episode/server names. These are library-provided names, not authored interface prose, and are preserved rather than rewritten. No ignore comments were added.
- The Settings tab strip shows all eight tabs at tablet width. Where the strip is narrower than about 1000 px the icons drop and the padding shrinks (a container query on the strip itself, because a container on the whole page would turn Bootstrap's fixed-position dialogs into page-relative ones); narrower still it scrolls with a fade on the cut edge, and `reprise-shell.js` scrolls only as far as it takes to show the current tab whole (it used to centre it, which hid the first tabs under the sidebar). `tests/e2e/test_settings_tab_strip.py` guards this.
- One name for the server list: Connections (Settings, then Connections). "Servers page", "Servers →" and "Media Servers" are not used in interface copy or in messages the owner can read.
- Review only means no false alarms. With preview thumbnails off for a server (and chapter thumbnails, Intro & Credits and loudness off) its Plex config folder is not required (`plex_config_folder_needed`), a wrong or read-only folder shows a muted note instead of a red error, its card says "Previews off", and Setup Health already advises nothing about thumbnails.
- A server that cannot be reached is explained in a sentence (what failed, what to check) with the technical text behind Details. One mapping serves the card, the edit dialog and the add flow.
- Expert controls are folded, not removed: Advanced settings starts with its processing groups closed, each with a one-line summary; setup step 4 keeps only the graphics card visible and folds worker groups and thumbnails under Advanced; the setup path step asks to check one real file before anything about Plex's own folder.
- "What's New" reads Reprise's own releases (`nphil/reprise`), not the upstream project's.
- The Setup guide never decides that a step is done. The page draws what `GET /api/reprise/setup-guide` reports, and the service marks a step done only from real configuration (a connected server, every chosen library's folders visible inside the container, episodes read into Reprise's own database). It never switches sending to Plex on and never edits a server; its buttons only open the existing place that does. A step that cannot work says why in plain words and names the exact folder, mount or setting, and Settings, Sharing refuses with the same sentence.
- The Setup guide is quiet on an install that is already set up. With an account and a connected server, `/` goes to the Library, the guide shows the three required steps done, and nothing is written. The banner for missing media folders is hidden on the guide page only, because step 2 says it better there.
- The Plex report is a page opened from the Library's header (`/reprise/report`, Library stays current in the sidebar), not a third destination. It draws what `GET /api/reprise/report` returns and decides nothing itself: the server does the comparison, so the page, the text format and an agent reading JSON agree. One list row per episode, linked to that episode's review in the Library (`/reprise?show=&season=&open=<id>`); the summary's flag chips double as filters. Every flag is a plain sentence ("Skips 52 s of story before the credits"), tones follow severity (problem is danger, needs attention is warning, sent to Plex is positive), and nothing on the page can change Plex.

## File identity: what makes a version stale (2026-11-03)

A version is the file's path, size, modification time, duration and stream layout. Three stat fields are recorded but are not part of it, each because a live library showed it moving without the content: the change time (a permissions, hard-link or mover pass), the device number (Unraid's user-share FUSE mount came back from a reboot with a new one on 4,218 of 4,239 files) and the inode (the mover gives a file moved between cache and array a new one). A replaced or edited file changes its size or modification time and still goes stale; the same version ID re-registered with a different change time, device or inode is the same generation. Whether a candidate reference is a hard link of the episode itself is checked live on disk at admission, not from the recorded numbers.

## Engine: the picture and the sound have their own offset (2026-11-03)

Problem. The recurrence engine required the sound to match sample-exactly at the picture's offset. Two files of the same show carry slightly different sound/picture sync, so on a real pair (Community S03E02 against E03) the picture votes put the intro at about +26.94 s while the sound lines up at +27.106 s, about four frames later. The sample-exact sound check found nothing at any proposal and no real intro was ever confirmed.

Design, the smallest that works:

- Per reference and per picture proposal, the engine searches for the sound offset within ±250 ms of the picture offset (six frames at 24 fps, far above same-source sync differences and small enough that sound and picture are still the same event). It decodes up to 12 s of the first mapped audio track from inside the proposal's support, centred on the target frames whose picture descriptors agree with the reference at the picture offset, cuts it into 1-s blocks and cross-correlates each with the reference's sound over the search window (float64 FFT, every native channel as one signal); the block with the highest normalised peak decides, so a probe that straddles shared and unshared sound (a 90-s opening window holding a 27-s intro) still finds the lag, and among that block's ties the whole-sample lag nearest the picture offset wins. A peak below 0.5 means no sound offset and the proposal is dropped before the slow checks.
- The strict, sample-exact sound identity is unchanged and runs at that sound offset; the picture identity runs at the picture offset; a range is confirmed only where both hold over the same target time. The search is a proposal mechanism like the picture votes: hints never constitute support. Identity gates, keep vetoes, anchors, admission, approval and publication are untouched, and a sync disagreement beyond the window stays unconfirmed (a keep), never guessed.
- Evidence records both offsets: `reference_offset_ms` (picture, which also places the reference window) and `sound_offset_ms`, each with its exact rational. Pieces are ledgered per reference, picture offset and sound offset.
- The verification profile becomes `native-signal-review-first-v5` with a `sound_offset` section, so every stored v4 result is stale and is re-analyzed on its next run.
- Frames pair within one container tick of the coarser stream (at least the ½ ms floor). Matroska keeps whole-millisecond timestamps, so two 24000/1001 fps files of the same material land 0 or 1 ms apart, alternating; with the fixed ½ ms the picture identity could never pair a real Blu-ray pair, whatever the pixels said (Community S03E02/E03: every frame pixel-identical within the limits, 17 of 40 one millisecond off). This is the picture twin of the audio audit's one-tick rule.
- The picture is checked only over the sound support's hull plus the change guard, starting at the last scanned frame at or before it. Support only counts where both signals match, so this is exact (a pair outside the span can neither support nor, with its guard, veto anything inside), and it stops a 1-s sound match from costing a 31-s picture decode (3–4 minutes a proposal on the CPU).
- The strict sound identity still compares every mapped track, but a track's low-frequency effects channel (`LFE`) may not veto alone: every other channel (FL, FR, FC, SL, SR, …) must pass, and the channels compared are recorded in the evidence (`checked_channels`, per track). Nitin chose this ("ignore subwoofer-only differences") after the measurement on Community S03E02 against E03: at the found sound offset the music channels agree at r = 0.99 (identity windows fail on 3–6 % of them) while the LFE is a different signal between the two AC-3 encodes (r swinging −0.57…+0.99, 60 % of its windows fail), so with every channel required only 1.1 s of the 27-s intro could be confirmed. The LFE carries no speech, is band-limited and is optional in reproduction (ITU-R BS.775), so no scene can be unique only there. A difference in any main channel still vetoes.
- For a continuous matched pair of frames the picture support is the target frame's span, clipped to the window. The earlier rule clipped it to the intersection of the two frames' spans, which with the one-tick pairing above left a one-millisecond hole wherever the rounding flipped between consecutive pairs (eight pieces over 1.7 s on the real pair), so no run was long enough to anchor. The reference span agrees with the target's within the pairing tolerance by the continuity check, so nothing is expanded beyond the tick.
- A Plex marker is the comparison's to propose only when the verified runs cover at least half of it. Otherwise it stays a Plex suggestion (approve-only, as before), the smaller confirmed fragments inside it are dropped and the result says how much was confirmed ("Comparing episodes confirmed only 1 second of it, less than half, so that part is not proposed on its own."). Nitin chose this over "any confirmed part makes it an ordinary proposal": with partial matches now possible, a one-second confirmed fragment would have replaced the whole-marker suggestion with a one-second skip and keeps, which helps nobody.
- Inside a Plex marker, short holes between confirmed pieces are filled ("fill the gaps, I'm ok missing really small 2 second jokes", Nitin). Between two lossy encodes about 2 % (Blu-ray) to 50 % (WEB-DL) of frames fail the per-frame picture limits and each failure vetoes ±250 ms, so a real intro confirms in fragments (Community S03E02 against E03: 5 s of the 27-s Plex intro). After the per-reference confirmation, a hole between two neighbouring confirmed runs is filled when ALL hold: it is at most 3.0 s; both neighbours are confirmed by Reprise (sound and picture); it lies entirely inside the Plex marker for the exact file; and no range the owner keeps overlaps it (the owner's kept ranges are read from the stored result when the analysis starts and are part of the analysis signature). Nothing outside the marker is ever filled, holes over 3 s stay protected keeps, and a file without a Plex marker is unchanged. A filled hole is its own `match` evidence window with `reason_code: "native_signal_bridged"`, `bridged: true` and `bridge_start_ms`, `bridge_end_ms`, `bridge_length_ms`; it carries the reference and checked channels of the run before it but no offsets (nothing was compared across it) and no reference range (so no comparison preview), and its skip range is an ordinary detector proposal the owner approves. The reasons say it in plain words ("Filled 4 short gaps (longest 2.1 s) inside Plex's intro."). Filled time counts as confirmed for the half a marker needs; if the marker is still under half, nothing is filled and it stays a suggestion.
- The verification profile becomes `native-signal-review-first-v7` (v6 added the `bridge` section: `max_gap_ms: 3000`; v7 renames its `plex_marker` flag to `suggested_window` and adds the `online` section), so every stored v5 and v6 result is stale and is re-analyzed on its next run.
- Online intro and credits times (IntroDB, SkipDB, TheIntroDB with a key; the existing Settings sources, plus the one "Look up intro times online" switch, on unless turned off) are asked once per episode (the target and each reference) before the comparison, through the Intro & Credits clients, pacing, daily budgets, series pauses and speed rules (`reprise/online.py`). An answer is remembered (`reprise_online_answers`, with the parser version; a "no entry" is asked again after 14-28 days; a refusal is never remembered). SkipDB's answer is matched to the file's length; IntroDB's and TheIntroDB's carry no length, so they are read on the file's own clock by the Intro & Credits rule (a 25 fps file against a film-rate release, 4.3 %), and a time that is not plausible for the file (an intro past 35 % of it, credits before its last quarter, a logo at the start) is dropped. Whatever fails, the episode simply has no online times and the analysis is unchanged.
- Online times do two things. As hints they ADD one more place to search in a reference (the target's window shifted by how far the reference's own online position sits from the target's, or around the reference's position when the target has none), tried only for a reference that confirmed nothing of that window where the usual 30 s neighbourhood was searched; sound and picture confirmation decide exactly as before, so with no online data the result and the speed are unchanged. As suggestions an online time is a suggested window like Plex's marker: it is compared the same way, the half-confirmed rule and gap filling apply to it, and what is not confirmed becomes an approve-only suggestion with origin `online`. Where it agrees with a Plex marker of the same kind within 5 s at both ends it is the same suggestion naming both; where it overlaps a Plex marker and differs, only Plex's is used and the result notes it (Nitin's "differs materially" case is a time away from every marker); the opening or ending stand-in window gives way to it so a keep over it cannot veto the suggestion.
- Online times never make an analysis fail. A hinted search is also skipped as soon as the stretch the databases expect in this episode is half confirmed. If the decoder cannot compare an online window (live: Community S03E02's credits time from SkipDB runs to the end of the file and the audio track ends before the picture, "Native audio decoder did not cover the window"), the window stays a suggestion with a plain note and the rest of the analysis goes on; a failing hinted search is noted and dropped. A Plex marker that cannot be compared still fails the comparison exactly as before.

## Engine: speed that cannot change a result (2026-11-04)

Nitin asked for the analysis to be much faster without giving up reliability. Every change below is exact, and each ships with a test that the output is identical; the ones that could change a verdict were measured and left out.

- Where the time went (S03E02, 3 references, NVDEC decode, host load 25 to 50): the picture check 54 % (3,129 frame pairs at about 0.43 s of CPU each; five of its six proposal checks were the always-empty neighbouring-frame offsets), scans 43 % (the ffprobe audit, a second full decode of each window, 15 %; the per-frame standard deviation 16 %), the sound 2 %. NVDEC saves about 20 % of ffmpeg's CPU per frame, not more: the frames still come back through system memory, and two `showinfo` taps cost about 13 ms of CPU per 1080p frame.
- `picture_excess` is the largest of the seven picture metrics over their limits and stops at the first one past `near_ratio` (a neighbouring frame fails on the first metric alone); `picture_metrics` stays as the reference every verdict is tested against.
- Profile v8 compares every pair of files in one canonical form (`canonical.py`; the exact definition, every limit and the measurements behind them are the text of `verification_profile.PROFILE_SPEC`). Picture: exact area means on a grid of at most 480x270 cells, 8-bit limited scale, the margin left out, within one colour class only; two files of one shape share the grid of the smaller, and a crop of up to 64 pixels is placed per frame pair from the two frames themselves (no header says which side was trimmed). Time: `Clock(rate, offset)` maps target time to reference time, the rate being 1 or the ratio of the two frame rates when within 5 % (a 25 fps speed-up), with a hold of one frame interval when the cadences differ (repeated frames). Picture limits: peak 96 and local4 24, about 1.5 times the largest clean value over about 10,300 measured frame pairs of the same footage in two files; a near miss (up to twice a limit) counts only while at most a quarter of the frames within half a second miss, anything further or unpaired breaks the run and vetoes a quarter second each side. Sound: each track folded to mono (LFE left out) at 16 kHz on the target's clock, the reference's level and sound offset measured per track; the three spectral limits are the larger of their old floor and a share of the quietest shared level (0.08, 0.03, 0.1), because two releases of one recording differ in proportion to the sound.
- The comparison's picture work moves to the NVIDIA GPU in two steps that change no number, so the rule set stays `native-signal-review-first-v9` (the canonical bytes are the same; a test builds a native and a reduced frame and compares their pictures bit for bit). Step 1, reduced frames (`reduction.py`, `NativeFrameReader(reduce=...)`): for a square-pixel 4:2:0 H.264 or HEVC stream whose whole frame is one canonical grid of 2, 4 or 8 samples to a cell (960x540, 1080p, 4K; not 720p, not a cropped or measured framing) the decoded frame stays on the GPU (`-hwaccel_output_format cuda`) and `scale_cuda` halves it log2(cell) times with a bilinear 2 x 2 average; 8-bit samples are first widened to 16 bits (an exact `nearest` conversion) so the averages keep their fractions. A cell's 16-bit mean is then its integer sum times a power of two, which is what the CPU's block sum gives (`reduce_planes`), and `canonical.picture` builds the same float32 picture from the cells (`Cells`, `_reduced_picture`) as from whole planes. 8-bit full range widens by 257, which is not exact: `_snap` recovers the whole-number sum and refuses a cell that is not one. Only about an eighth of the bytes reach the CPU, and the conversion, the `showinfo` checksums and the pipe copy handle that eighth: ffmpeg's own CPU per frame fell from about 13 ms to 2 ms (H.264, 1080p) and from 29 ms to 2 ms (HEVC 10-bit, 1080p). It is held to the CPU at three levels. At startup the GPU reduces the two reference clips at every cell size and each cell must equal numpy's reduction of the CPU decode, with FFmpeg's own record of the frames (timestamps, colour declarations and plane checksums, which are Adler-32 seeded with 0) equal to what the cells imply. Every frame on the pipe is checked the same way. A reduced decode that fails is repeated by the same GPU without the reduction and then by the CPU, whose frames must reproduce the ones already delivered (compared in reduced form), and three disagreements in a row withdraw the reduction for that codec until restart. `REPRISE_GPU_REDUCE=0` turns it off.
- Step 2, batched pair metrics (`gpu_pairs.py`, `cuda_compare.py`, `cuda_kernels/compare.cu`): the seven picture metrics (`PICTURE_METRICS`) of up to 128 frame pairs are computed per batch by two kernels (cells to the float32 picture, then the metrics of every pair at once, with float64 sums and `--fmad=false` so each operation rounds as the CPU's does); only seven numbers per pair come back. All 2,947 metric values of 421 real pairs (identical frames, neighbours, frames brightened by 0.5 to 7.2 code values, and frames of two different episodes) equalled the CPU's to the last bit and no verdict changed. Only two ratios decide anything (1, agrees, and `near_ratio`, a near miss), so a pair whose ratio is within 1e-5 (relative) of either is measured again on the CPU, and a last-bit difference could never change a verdict; any GPU error (no GPU or driver, kernels missing, a failed launch, out of memory, numbers that are not finite) sends the batch and the rest of the window to the CPU's `picture_excess`. The kernels are PTX built from our `.cu` by `tools/build_reprise_ptx.py` (NVRTC of CUDA 11.8, `compute_61`, the driver compiles it for newer cards) and are loaded through `libcuda.so.1` with ctypes: no CUDA toolkit, no Python GPU library and nothing of NVIDIA's redistributed; the container needs `NVIDIA_DRIVER_CAPABILITIES` to include `compute`. The removed v7 verdict decided on the GPU from native planes; this only computes the CPU's numbers faster and every decision is still made on the CPU's side of the limits. `REPRISE_CUDA_COMPARE=0` turns it off.
- The GPU's memory is a loan. A session (one CUDA context) opens when an analysis first asks for a batch and closes, freeing the context and everything in it, when the last running analysis ends (`acceleration.compare_lease`), so nothing lives between jobs. Its budget is `min(reprise_gpu_vram_cap_mb, free memory at that moment - 1 GiB)`: the setting defaults to 2048 MiB (256 to 16384, owner setting `gpu_vram_cap_mb`), a budget under 64 MiB means the card is not used, and a chunk takes at most half the budget (about 1.8 MiB per distinct frame pair; 232 MiB for a chunk of 128 pairs over 256 frames, plus about 148 MiB for the context). A CUDA out-of-memory halves the chunk and retries, then hands the work to the CPU; nothing owned by another process is ever touched. A self-test (the kernels on a built-in pair against the CPU's numbers, about 0.6 s) runs once per process; a mismatch (`GpuMismatch`) switches the comparison off until restart. The tests run without a GPU (a fake driver for the out-of-memory and shrink paths, numpy for the reduction) and the GPU tests skip cleanly.
- Measured on the NAS (the P40 shared with other work, host load 15 to 19, runs alternated) on one real pair, The Apothecary Diaries S03E05 against S03E06, 1080p H.264, the 20-second intro window (528 and 720 frames scanned, 515 frame pairs): today's code took 137.7 and 129.9 CPU s (62 s and 114 s of wall time, the second during a load spike), reduced frames 72.7 and 75.5 CPU s (35 s and 41 s), reduced frames with GPU pair metrics 72.2 and 69.9 CPU s (42 s and 39 s); all six runs confirmed the same range (793 to 21,932 ms) and the same picture support. Of those seconds ffmpeg's video went from 34.6 to 6.7, Python's frame reception from 19.0 to 2.9, `canonical.picture` from 16.3 to 1.0 and `picture_excess` from 4.0 to 0 (515 pairs, none measured again). What is left is mostly the ffprobe audit (41 s of 70), which decodes each window again on the CPU as the independent check on the GPU's decode and is deliberately unchanged, and the sound and audio stages (14 s, mostly Python loops that drain the audio; the FFT was measured negligible and stays on the CPU). Candidates for the next saving, none done: one audit of the target window shared by its up to three references, copying frames out of the pipe without an intermediate buffer, and fewer Python loops in the audio drains.
- The ffprobe audit of a window runs in a thread beside the reader's ffmpeg. The reader compares its timestamps with the audit's when the stream ends, a failed audit is raised there (or at exit when the stream was never read), and no consumer takes frames from a reader that exited with an error, so nothing is accepted earlier than before.
- The references of a window are searched by up to three worker threads (`REPRISE_ANALYSIS_WORKERS`), fewer when the container's process limit has no room for that many. The shipped compose file and Unraid template cap the container at 128 processes and threads, which count every thread of FFmpeg and Python alike; a search holds up to about 32 of them at its busiest, so `container_limits.process_headroom()` (the cgroup's `pids.max` less `pids.current`) sets the number to `(room - 16) // 32`, never fewer than one, and no limit means the configured number. Every FFmpeg the exact reader starts also limits its output side to one thread (`-threads 1` after `-i`, as well as the decoder's before it): a bare output defaulted to one encoder thread per CPU of the host, so one decode held 37 threads (55 on the GPU, 21 for audio) on a 16-CPU host, a thread that could not start made FFmpeg log an error, and the exact reader rightly fails any decode that logs one ("Native frame metadata failed"). The failure now carries FFmpeg's own line. Each search returns its verified runs and notes; they are merged in reference order, and the first search to fail in that order is the failure, so the result does not depend on timing. A search waits on its unfinished futures only (waiting on a set that holds a finished one is a busy loop that made the analysis five times slower). Hinted (online) searches are decided after all default ones are merged, as before.
- The scan cache keeps a scan's hints per file generation (`MediaVersion.id`), stream and verification-profile fingerprint. A hint is a pure function of one decoded frame, so a window inside stored frames is answered from them (checked against real decodes), still followed by the generation check. Another generation of the same path replaces the entry, a profile change drops it, and it is bounded.
- Spreading references over the P40 and the Intel iGPU was measured fairly, three reference scans at once, back to back, with identical output: all on the P40 383 s and 386 s (111 ms of CPU per frame); split P40, Intel, P40 471 s and 501 s (122 ms); all on Intel 411 s (137 ms). The Intel decoder is almost idle (about 3 to 9 % busy): VAAPI decode costs 1 ms of CPU per frame, but the copy of each decoded 10-bit surface to system memory costs 24 to 32 ms, and the P010 to yuv420p10le conversion only 6 to 14 more, so there is nothing to win by converting in our code. It stays off (`REPRISE_SPREAD_DECODERS=1` turns it on).
- Rejected because they could change a verdict or do not pay: dropping the neighbouring-frame proposals (adjacent frames of a static scene pass), an audio-only gate that skips a reference's picture scan, scanning fewer frames to vote the offset (decode cost does not fall when frames are only sampled), and stopping at the first reference that confirms the whole window (it changes which notes and failures are reported).

## Engine: a marker that runs to the end of the file, and one odd sibling (2026-11-19)

The first full Community season 3 run (22 episodes, each against its three nearest) showed two faults that were the engine's, not the files'. Both fixes only add comparisons the evidence already allows; no limit, vote or identity rule changed, so the verification profile is unchanged.

- A window that runs past the end of a sound stream is compared up to where the stream ends. Live, E06, E09, E11 and E22 failed whole ("This episode can't be compared exactly with the others, so nothing could be confirmed", detail "Native audio decoder did not cover the window"). Plex ends a credits marker at the container's duration, which for these Blu-ray rips counts the subtitle streams, so it lies past both streams. Measured on the 22 files: in 14 the sound ends 15 to 40 ms before the picture's last frame, in 7 it runs 0.59 to 0.89 s past the picture, and the sound search reads 250 ms beyond the last shared picture frame. The strict reader refused any window its stream did not hold completely; an online window swallowed that (the note above), a Plex window failed the analysis. E06's own sound outlasts its picture, but the references nearest to it (E04, E05, E07) end early.
- The rule is the reader's, opt-in (`to_end`, default strict, used by the sound search and the strict sound identity only). The short window is accepted only when the decoder delivered exactly as many samples as the separate metadata audit counted, with no decoder error and no discontinuity, and the window starts inside the stream; a window that starts at or after the end, a gap in the timeline, a truncated file, a decoder error or a decode that disagrees with the audit still fail closed. Identity runs over the two sounds in step and stops where either ends, so support exists only where both sounds exist and nothing is claimed beyond the shorter one (the last few milliseconds are outside any range, which is where an ending ends anyway). The picture check, its limits and the half-of-a-Plex-marker rule are untouched. This supersedes the remark in the 2026-11-03 section that a credits window running to the end of a file whose sound ends first cannot be compared; a Plex marker whose stretch is really missing from the sound still fails as before.
- References: the three nearest episodes used to be chosen first and the ones that cannot be compared exactly (another video codec or colour depth, another sound layout, unreadable) dropped afterwards, with nothing taking their place. Live, E17, E19 and E20 each lost the one reference E18 (H.264 8-bit among the season's HEVC Main10) and compared with two; E18 itself had no usable reference. Admission now returns every admissible episode, nearest first (by episode number, lower first on a tie, one file per proven episode), and the analysis walks that list, skipping an episode it cannot compare exactly, until it has three. It stops looking at three, so a normal season probes three files as before. The result counts what was passed over and why ("1 other episode of this season has a different picture format, so it was left out of the comparison."); an episode whose own format differs from all the others says so in one sentence instead of "None of the other episodes of this season could be used for the comparison".
- The service gives the analysis the whole list but asks the online databases, and signs the inputs, for the three nearest only (every extra lookup is a request to someone else's server), so a reference that took the place of a nearer one has no online hints. An episode in another picture format is still not compared with its neighbours: that would need frame limits designed for 8-bit against 10-bit pictures, which nothing here measured.

## Recovery: an analysis resumes after a restart (2026-11-21)

Problem. Restarting the server ended the 54-episode analysis of The Apothecary Diaries (job 907abad5) at 29%: 15 episodes complete, one cut off, 38 never started, and the Library said "Job failed". A restart leaves the job `running`; the generic start-up pass found it, and because `auto_requeue_on_restart` was off it marked the job failed ("Job was interrupted by server restart"). Nothing kept the episodes still to do, so even a manual Resume would have started over.

- The queue is part of the job. `reprise/recovery.py` (pure functions on a dict, no I/O) owns `config["reprise_queue"]`: the episode list (`ids`, saved once; a library analysis saves what its scan returned and is never scanned again), the position (`next`), attempts per episode, the episode being read (`running`), outcome counts (results, file left out, refused, set aside), the recent automatic resumes and the recovery note. `RepriseService._queue_set` writes it through the job manager's `merge_job_config`, only when it changed, always taking the queue lock before the manager lock. Job responses carry the note (`recovery`), never the list. A job saved by an older version has no queue: the first start re-reads its request, and the store says which episodes already finished.
- Start-up owns the decision, independent of `auto_requeue_on_restart`. `JobManager._load_jobs` keeps interrupted Reprise jobs `pending` and hands them over (`consume_interrupted_reprise_jobs`); the generic requeue/fail logic never sees them. `recover_after_restart` notes the restart and sets each job `waiting`; a job the owner had paused stays paused. A timer (`start_resume_timer`, thread `reprise-resume`, first look after `reprise_resume_delay_seconds`, default 120, then every 30 s) calls `resume_after_restart`. `_start_job_async` refuses a `waiting` job, so nothing but that pass or the owner's Resume starts it.
- Unavailable media is waited for, not counted. A job resumes only when Plex answers and a library folder has files (`_resume_blocker`) and the global pause is off. Otherwise it stays `waiting` ("Waiting for your media folders…" or "…for Plex…"), and after 30 minutes it pauses (`media_unavailable`). None of that counts as an attempt or a resume.
- Finished work is never redone. The run continues from `next`; an episode whose result was saved just before the kill, but not yet noted in the queue, is found in the store (`RepriseStore.finished_in_job`: a `complete` run for that job) and counted, not analyzed. The episode that was in flight had its run ended as interrupted at start-up (`fail_stale_analyses`) and is analyzed again.
- Attempts are bounded. An attempt is counted when an episode begins, so a hard kill keeps it. An episode that already had two is set aside, not tried a third time: a skipped item and a per-episode outcome `set_aside` ("Skipped after 2 interrupted attempts — analyze it again to retry"), its result row `cancelled` with that reason, and the job moves on and ends `completed` with a warning. A set-aside episode is not progress.
- The restart-loop guard. Each automatic resume records how many episodes had finished. The next automatic resume is refused, and the job paused (`kept_stopping`: "Analysis paused: it kept stopping. Resume when ready."), when the last 3 resumes inside 15 minutes all show the same finished count. Until the job is analyzing (a refresh, or a library job still reading its library) there is no queue to measure, so a single earlier resume pauses it: it re-runs once. The owner's Resume clears the history and restarts it; attempts stay, so a set-aside episode stays set aside until it is analyzed again on purpose.
- Deterministic errors are recorded once. A file that is missing or changed, an unsupported file, or a refusal by the engine is noted for that episode (skipped item, per-episode outcome) and settled in the queue; a resume never retries it. These no longer fail the whole job: it ends `failed` only when every episode that ran was refused and none produced a result, which keeps the reason on the job as before. An owner-cancelled job is `cancelled` and persisted at once, so it never reaches the interrupted list.
- A stop is a checkpoint (SIGTERM). `shutdown.on_shutdown(checkpoint_for_shutdown)` gives back the episode each running job was reading, one small write per job (s6 kills about 3 s later). In the run, after an analysis returns while the app is stopping, its draft is dropped whatever its status (ffmpeg dies with the app, so even a "complete" one cannot be trusted): the episode's run ends `cancelled` with "Analysis was interrupted before it finished", never `failed`, nothing partial is saved, the attempt is given back, and the job stays `running` for the next start. A deploy therefore never counts toward setting an episode aside.
- Refresh and preview. A refresh has no queue; it is re-run once by the same pass and the same guard (a second interruption pauses it). A preview is not resumed (the person who asked is gone) and ends `failed`: "This preview was interrupted by a restart. Create the preview again."
- Settings: `reprise_auto_resume` (default `true`; `false` leaves the job paused with "Analysis was stopped by a restart. Resume when ready.") and `reprise_resume_delay_seconds` (default 120, 0 to 3600). Neither has a page control yet.
- Rejected: retrying forever with a back-off (a crash that is the episode's own, such as a file that kills ffmpeg, would repeat with no useful work; the two caps bound the waste at two attempts per episode and three resumes per job); starting a new job for the rest (it loses the Activity history and counts, and leaves the old one failed); keeping per-episode status in the Reprise results store (the store is the truth about results; the queue is job state and shares the job's cancel, delete and prune).
- Tested without waiting or luck (`tests/reprise/test_resume_after_restart.py`): the process "dies" by raising `SystemExit` inside a fake analysis, a restart reopens the same config folder with a new job manager and service, and the clock is passed in.

## Autopilot: automatic intro and credits (2026-11-22)

Problem. Reprise only worked when asked. Someone had to press Analyze, review every range, approve it and send it to Plex, one episode at a time, and a new episode from Sonarr or Radarr waited until someone remembered. For a library of thousands of episodes that never finishes. "Automatic mode" (code name autopilot) lets Reprise do the part that is safe to do alone: read every new file, work through the rest of the library in the background, and send to Plex only the ranges it is sure about. It has to do this without becoming a second program to look after, and without ever writing a guess into Plex.

- One scheduled job, nothing else. `reprise/autopilot.py` is ticked by an internal APScheduler interval job, `__reprise_autopilot` (`web/scheduler.py`, `run_reprise_autopilot`), every minute, first run 90 s after start-up so the app finishes starting and resumes interrupted work first. There is no cron entry, no extra thread and no AI session. `max_instances=1` and a lock keep one pass at a time. A pass does four steps in order (look for new files, plan the backfill, send sure matches, watch for problems); a step that raises is logged and the next still runs. The app builds it once (`RepriseService.autopilot`); if that fails it logs once, the rest of Reprise works as before, and the settings API says `autopilot: null`.
- New files, pushed and pulled. Sonarr's and Radarr's "Reprise" webhook (a message the app sends to Reprise when something happens) calls `_nudge_reprise` (`web/webhooks.py`) from the shared webhook-job path, whatever the older per-library webhook settings say. The nudge only remembers the file's path (at most 500; the webhook's own delay up to 300 s, plus 60 s for Plex to scan it). The look itself reads Plex's listing (`RepriseService.list_library`, the same paged read the refresh uses, nothing registered) of every enabled movie and TV library and compares each file's Plex part id, size and duration with what Reprise already read (`RepriseStore.bound_parts`, one query). It queues a file only when that differs or is new, the file can be opened on this machine at the size Plex reports (a file still being copied is skipped), no queued job already names it, and it is a single-part file. A file Plex does not list yet is looked for again every 2 minutes, up to 6 looks in all. A full look every 30 minutes (and one on the first pass after a start) finds what a webhook missed. Plex is only ever read.
- Priorities reuse the existing queue. New files go in jobs of 10 at the owner's incoming-job priority (`incoming_job_priority`, normally high), so a fresh import jumps the queue. More than 50 files in one look is a backlog: jobs of 50 at low priority, at most 4 per pass, none while 8 of Reprise's own jobs are waiting. The jobs are ordinary library analyses (`trigger: autopilot`, shown as "Reprise: new files"), so pause, cancel and the resume-after-restart of the section above all apply. Autopilot jobs skip a file whose analysis is already complete and current, so a file is never analysed twice. A file queued before is retried only after 30 minutes, then 2 hours, then 8 hours (four queueings in all, counted per file size, so a changed file starts fresh), each alone at low priority, at most 5 per pass. In these jobs a file that cannot be read yet is noted and no longer holds back the rest; the next look tries it again.
- Backfill. When its switch is on, processing is not paused and none of Reprise's own jobs is waiting or running, `plan_backfill` takes the next 5 files that `RepriseStore.unanalyzed()` lists (read, but never analysed, or failed, or cancelled, or analysed by an older method) and queues them as one low-priority job (`source: autopilot_backfill`). Order: most-watched shows first by Plex's `viewCount` summed over the show, then the most recently watched, then A to Z; a show's episodes in season and episode order; then films; then specials (season 0). The play counts come from every look at Plex and are kept in `reprise_autopilot_plays`. Plex's counts cover only plays by the Plex account Reprise uses. A file chosen is counted and, if it fails, comes back after 1 hour, then 6 hours, and is left alone after 3 picks.
- Sending is a second, separate pass (`reprise/autosend.py`). It looks at each complete result of the current method once per revision (up to 40 a pass), and sends at most 3 episodes a pass, one at a time. It reuses the manual publisher, so every publication check still applies. The gates:

  | Gate | What must be true | If not |
  |---|---|---|
  | Switches | "Send sure matches to Plex automatically" is on (default), "Allow sending to Plex" is on, and no earlier write was left half-finished. | Nothing is sent; the Settings status line says why. |
  | Kind of item | A TV episode: never a film, never a special (season 0). Its analysis is complete and current. | A film or special is left for you; an analysis not current is looked at again in 30 minutes. |
  | History | No earlier change for it was sent (by you or Reprise), undone or left unfinished. | Left for you. |
  | Your decisions | Nothing in it is approved. No range you made, locked, reviewed or overrode overlaps the run, and none of your keeps does. | Left for you, with a plain note. |
  | Evidence | The ranges are detector skips, confirmed by picture and sound, still proposed. A Plex or online suggestion never qualifies, nor does a gap that was filled between two confirmed pieces. | Left for you. |
  | One run per kind | The confirmed pieces of a kind touch exactly, so they make one unbroken run. | That kind is left for you. |
  | Dry run | Plex's exact projection rule, run on a trial copy, gives back exactly that start and end for every audio track, and the tracks agree. | That kind is left for you. |
  | Backup | Today's backup of Plex's database exists. | Nothing is written; you are alerted. |

  Only the kind that passes is replaced: sure credits leave Plex's intro exactly as Plex has it, and the reverse. A decision of "left for you" is final for that revision of the result; a new analysis is looked at again.
- How one send goes. The attempt is recorded first, so a restart in the middle can find it. `RepriseStore.auto_approve` approves the pieces on Reprise's own authority (it records no owner override, which is what keeps "yours" and "Reprise's" apart), then the publisher prepares and applies with the actor `reprise-auto`, so the change is journalled and can be undone like any other. If it fails, the journal says where it stands. Applied: counted as sent. Never reached Plex: the change is closed and `auto_unapprove` puts the approval back (only on a range you never touched). Plex or its database unreachable: nothing is recorded and sending waits 5 minutes. Plex refused: sending pauses for 30 minutes, or 6 hours after 3 refusals in a row, and you are alerted. A result that cannot be told: the change is marked uncertain, never repeated or undone from here, sending pauses 6 hours and you are alerted. A send that failed for another reason is tried again after 6 hours, and left for you after 3. A restart mid-send is finished or taken back at the next pass (`_finish_interrupted`).
- The daily backup (`reprise/plexbackup.py`). Before the first automatic write of each UTC day, Plex's library database is copied with SQLite's online backup API, which is safe while Plex runs (a plain file copy is not), to `plex-db-backups/` in Reprise's config folder (`/config/plex-db-backups/`). The copy is written as a hidden file with mode 0600, checked with `PRAGMA quick_check`, and only then renamed to `com.plexapp.plugins.library.db.<time>.bak`, so a backup that exists is a whole, readable one. The newest 7 are kept. It needs twice the database's size free. If it cannot be made nothing is written to Plex, you are alerted, and it is tried again in 30 minutes.
- Films are asked about credits only. A film has no other episodes to compare with, so there is no detector for it yet: its credits come as suggestions from Plex's own credits marker and from the online databases that know films (SkipDB, TheIntroDB). A suggestion waits for your approval and is never sent automatically. Scenes during or after the credits stay protected as they are for episodes.
- Phone alerts (`reprise/alerts.py`). The alert goes to ntfy at `https://ntfy.nateshome.net`, topic `homelabber`. The token is read from the file `ntfy-token` in the config folder (`/config/ntfy-token`, mode 0600 expected; Reprise does not check the mode) at the moment of sending, and is never cached, stored or logged. The server and topic are fixed in this version. An alert is one message per problem: it opens once, repeats are silent, and one that never arrived (alerts off, no token, server down) is tried again every 10 minutes. When the problem clears Reprise sends a plain "fixed" follow-up, but only if the first alert reached you. State lives in the app database, so a restart neither repeats nor loses an alert. A failed send never raises into the work that asked for it.

  | Alert | When | Fixed when |
  |---|---|---|
  | Episodes set aside | An analysis set episodes aside after repeated failures. Batched per job, sent 2 quiet minutes after the last one or when the job ends. | They are analysed, or gone from the library. |
  | An analysis paused | Reprise paused a job because it kept stopping. | The job runs again or finishes. |
  | Plex can't be reached | Plex has been unreachable for more than 1 hour; also when Plex answers but its library list could not be read for more than 1 hour. | It answers, or the library reads, again. |
  | Plex refused an automatic change | Plex turned a change down. | A later automatic change is accepted. |
  | Plex backup failed | The daily database backup could not be made. | A backup succeeds. |
  | Low disk space | Under 2 GB free where `/config` lives. | 3 GB free or more. |
  | A change that can't be told | An automatic change may or may not be in Plex. One alert for each such change. | Never by itself: sending pauses for 6 hours and the change is yours to check in Reprise. |

  Problems are asserted again on every pass (`Concerns` in `reprise/autostate.py`), which is how an undelivered alert is retried. Plex and disk are checked every 5 minutes.
- Settings. The Sharing page has an "Automatic work" panel with three plain switches: send sure matches to Plex automatically, work through the rest of the library quietly, and send an alert when something needs attention (with a "Send test alert" button, which sends even when alerts are off). A status line shows the files waiting, the last look at Plex and the last alert. The keys are `reprise_auto_send`, `reprise_backfill` and `reprise_alerts_enabled`, all `true` until changed. Looking for and analysing new files has no switch of its own: it only reads. API: [reprise-api.md](docs/reprise-api.md#automatic-mode). The Plex report shows an episode Reprise sent by itself as "Sent to Plex automatically" (`published_auto`).

Known limits.

- A later full-library rescan marks sent episodes "Plex changed" (existing behaviour; the report and Library still say so).
- Plex's `viewCount` covers only the plays of the account Reprise uses, so the backfill order reflects that account's watching, not the household's.
- A webhook can arrive before Plex has scanned the file. The retries (every 2 minutes, up to 6) and the 30-minute look cover it.
- Films get no detector, only suggestions that wait for you.
- The first automatic pass after an update may send episodes that were analysed earlier and qualify now (after the daily backup). Turn the switch off first to review them by hand.
- The ntfy server and topic are fixed; only the token is configured.
