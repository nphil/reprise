# Reprise interface

## Direction

Reprise is an operating tool, not a promotional page. The user confirmed a **library-first, code-led** interface. There is no approved visual comp and no comp-fidelity claim.

The surface uses the Lucent v2 web adaptation, Rosé Pine dark/light roles and locally bundled Manrope. `media_preview_generator/web/static/css/reprise-tokens.css` is the token layer.

### One shell, two destinations

Every signed-in page extends `base.html` and gets the same sidebar. It has two destinations, **Library** and **Settings**. Its footer holds, in order: the Plex safety chip ("Review only" or "Plex publishing is on", from `GET /api/reprise/settings`), notifications, theme, Help, the tour and Sign out. On phones the sidebar becomes a top bar with a menu button. Sign-in and the Welcome page are standalone (`_auth_page.html`); the setup wizard and the sign-out confirmation use the base without the sidebar (`rp_bare`).

Everything administrative lives under Settings, reached by one tab strip: Connections, Sharing, Automation, Advanced, Jobs, Logs, Inspector and Library health. Nodes belongs to Advanced and Webhook activity to Automation, and highlight those tabs. Plex publication and playback API clients ("Add an app") are on Sharing, not on the Library page, so the Library page has one job.

The inherited upstream pages keep their layouts. `reprise-shell.css`, loaded last, repaints them: it maps the upstream and Bootstrap variables (`--bs-*`, `--plex-orange*`, `--surface*`, `--t-*`) onto the `--lu-*` tokens and restyles cards, buttons, forms, modals, dropdowns, tables, badges and alerts. A page must never load the upstream navbar, its sponsor or "help the upstream project" links, or a "Media Preview Generator" page title. `tests/test_shared_shell.py` enforces this for every page.

### The primary flow

Library → pick an episode → Analyze → review the proposed intro and credits ranges → approve → save. Selecting several episodes analyzes them as one action. Approval stays separate from analysis and from publication.

## Library behavior

- The episode list is the left pane (sticky and bounded on wide screens, first in document order on narrow ones). Each row has a checkbox, the episode, and one plain status chip: Not analyzed, Waiting to analyze, Analyzing N%, N to review, Reviewed, Nothing to skip, Nothing found, Analysis failed, File changed, Cancelled, or Not supported. Counts reflect saved decisions only.
- Plex, media, part and audio identifiers are hidden. They appear only under the collapsed **File details** disclosure of the open episode.
- Every analysis outcome is a sentence with a next step, using the plain reasons the API returns (`reasons`, `outcome.message`, job `message`). The technical second line sits under **Details**. "Nothing found" says what was compared; a failure says why and offers Try again. A file that changed on disk offers Refresh library, not Analyze, because the backend refuses stale analysis.
- Activity, in the library pane, shows analysis, previews and library refresh jobs with progress and Pause, Resume and Cancel. A pause request is labelled pending until confirmed and offers Resume; terminal states remove controls. Only a refresh observed active triggers a one-time list reload when it finishes. It polls every 2.5 seconds while something runs and every 10 seconds otherwise.
- The page header says whether analysis decodes on a GPU or the CPU (`acceleration.label`) and offers "Use CPU only" or "Use GPU when available".
- Existing ranges start collapsed in native `details`, sorted by start time. Their summaries expose action, type, time bounds, decision and lock state. Fine timing, action, type and lock sit under "Fine-tune this section". New unsaved manual keep ranges open immediately.
- A section Plex suggested (`origin: "plex"`) is never presented as something Reprise found. It carries the badge "Plex suggestion" (after approval "Plex suggestion · approved by you"), an outlined, unfilled bar on the timeline, and its own count in the list ("N to review" counts Reprise-confirmed skips only; "N Plex suggestions" counts the rest, and both can show). Choosing Approve on it opens an inline question, "Plex found this, Reprise could not confirm it. Approve it only if it is right.", with "Approve it" and "Not now". Only after that answer does the save send `acknowledge_plex_suggestion: true`, and only for that range: editing an already approved Plex range counts as the same deliberate act, while ranges re-sent untouched, rejected or undecided carry no flag. There is no approve-all, so a bulk action can never approve a Plex suggestion.
- Range objects retain their own view while editing; typing and native select changes do not replace the focused field. Unsaved identity does not depend on array position.
- The save bar appears only when there are unsaved changes. The timeline is a visual overview; exact timings and decisions are in the range list.
- The selected episode is marked independently of focus, including after library reloads. `?search=` opens the Library filtered to a title (the Inspector links here).

## Intentional decisions

- Navigation is two items on purpose. A third top-level item needs a task that Library and Settings cannot hold.
- The Inspector's older "Check intro & credits" job is offered only when some server has that detector switched on. Otherwise it links to Analyze in Library, because that job checked nothing and looked as if it had.
- The master/detail review and lower administration sections scroll normally. They are not forced into a single desktop viewport. On narrow screens the library precedes review, with an "All episodes" link back; six range editors no longer all expand on arrival.
- Upstream documentation links (Nodes guide, Emby guide) still point at the preserved upstream guides. Reprise's own Help, release and update links point at `github.com/nphil/reprise`.
- The rendered Impeccable detector found one advisory earlier: repeated em dashes in explicitly synthetic episode/server names. These are library-provided names, not authored interface prose, and are preserved rather than rewritten. No ignore comments were added.

## File identity: what makes a version stale (2026-11-03)

A version is the file's path, size, modification time, duration and stream layout. Three stat fields are recorded but are not part of it, each because a live library showed it moving without the content: the change time (a permissions, hard-link or mover pass), the device number (Unraid's user-share FUSE mount came back from a reboot with a new one on 4,218 of 4,239 files) and the inode (the mover gives a file moved between cache and array a new one). A replaced or edited file changes its size or modification time and still goes stale; the same version ID re-registered with a different change time, device or inode is the same generation. Whether a candidate reference is a hard link of the episode itself is checked live on disk at admission, not from the recorded numbers.

## Engine: the picture and the sound have their own offset (2026-11-03)

Problem. The recurrence engine required the sound to match sample-exactly at the picture's offset. Two files of the same show carry slightly different sound/picture sync, so on a real pair (Community S03E02 against E03) the picture votes put the intro at about +26.94 s while the sound lines up at +27.106 s, about four frames later. The sample-exact sound check found nothing at any proposal and no real intro was ever confirmed.

Design, the smallest that works:

- Per reference and per picture proposal, the engine searches for the sound offset within ±250 ms of the picture offset (six frames at 24 fps, far above same-source sync differences and small enough that sound and picture are still the same event). It decodes up to 12 s of the first mapped audio track from inside the proposal's support, centred on the target frames whose picture descriptors agree with the reference at the picture offset, cuts it into 1-s blocks and cross-correlates each with the reference's sound over the search window (float64 FFT, every native channel as one signal); the block with the highest normalised peak decides, so a probe that straddles shared and unshared sound (a 90-s opening window holding a 27-s intro) still finds the lag, and among that block's ties the whole-sample lag nearest the picture offset wins. A peak below 0.5 means no sound offset and the proposal is dropped before the slow checks.
- The strict, sample-exact sound identity is unchanged and runs at that sound offset; the picture identity runs at the picture offset; a range is confirmed only where both hold over the same target time. The search is a proposal mechanism like the picture votes: hints never constitute support. Identity gates, keep vetoes, anchors, admission, approval and publication are untouched, and a sync disagreement beyond the window stays unconfirmed (a keep), never guessed.
- Evidence records both offsets: `reference_offset_ms` (picture, which also places the reference window) and `sound_offset_ms`, each with its exact rational. Pieces are ledgered per reference, picture offset and sound offset.
- The verification profile becomes `native-signal-review-first-v5` with a `sound_offset` section, so every stored v4 result is stale and is re-analyzed on its next run.
- Frames pair within one container tick of the coarser stream (at least the ½ ms floor). Matroska keeps whole-millisecond timestamps, so two 24000/1001 fps files of the same material land 0 or 1 ms apart, alternating; with the fixed ½ ms the picture identity could never pair a real Blu-ray pair, whatever the pixels said (Community S03E02/E03: every frame pixel-identical within the limits, 17 of 40 one millisecond off). This is the picture twin of the audio audit's one-tick rule.
- The picture is checked only over the sound support's hull plus the change guard, starting at the last scanned frame at or before it. Support only counts where both signals match, so this is exact (a pair outside the span can neither support nor, with its guard, veto anything inside), and it stops a 1-s sound match from costing a 31-s picture decode (3–4 minutes a proposal on the CPU).
- The strict sound identity still compares every mapped track, but a track's low-frequency effects channel (`LFE`) may not veto alone: every other channel (FL, FR, FC, SL, SR, …) must pass, and the channels compared are recorded in the evidence (`checked_channels`, per track). Nitin chose this ("ignore subwoofer-only differences") after the measurement on Community S03E02 against E03: at the found sound offset the music channels agree at r = 0.99 (identity windows fail on 3–6 % of them) while the LFE is a different signal between the two AC-3 encodes (r swinging −0.57…+0.99, 60 % of its windows fail), so with every channel required only 1.1 s of the 27-s intro could be confirmed. The LFE carries no speech, is band-limited and is optional in reproduction (ITU-R BS.775), so no scene can be unique only there. A difference in any main channel still vetoes.
- For a continuous matched pair of frames the picture support is the target frame's span, clipped to the window. The earlier rule clipped it to the intersection of the two frames' spans, which with the one-tick pairing above left a one-millisecond hole wherever the rounding flipped between consecutive pairs (eight pieces over 1.7 s on the real pair), so no run was long enough to anchor. The reference span agrees with the target's within the pairing tolerance by the continuity check, so nothing is expanded beyond the tick.
- A Plex marker is the comparison's to propose only when the verified runs cover at least half of it. Otherwise it stays a Plex suggestion (approve-only, as before), the smaller confirmed fragments inside it are dropped and the result says how much was confirmed ("Comparing episodes confirmed only 1 second of it, less than half, so that part is not proposed on its own."). Nitin chose this over "any confirmed part makes it an ordinary proposal": with partial matches now possible, a one-second confirmed fragment would have replaced the whole-marker suggestion with a one-second skip and keeps, which helps nobody.
